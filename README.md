# popingui

**Массовая проверка доступности с диагностикой способа блокировки**

DNS · PING · TCP · TLS/SNI · HTTP · UDP/QUIC

[English](README.en.md) · [Скачать для Windows](../../releases/latest) · [Методики](docs/methodology.ru.md)

</div>

![Главное окно popingui](docs/assets/screenshot.png)

Обычный ping не объясняет, почему сайт не открывается. popingui проверяет путь по шести
сетевым слоям и формулирует практический вердикт: подмена DNS, блокировка IP/порта,
DPI-обрыв TLS по SNI, подмена сертификата, HTTP-заглушка, несовпадение ожидаемого текста
или проблема UDP/QUIC.

## Возможности

- массовый импорт адресов, URL и `host:port`;
- индивидуальный набор слоёв для каждой цели;
- непрерывный опрос с регулируемыми интервалом, таймаутом и параллельностью;
- история задержки, аптайм и подробный протокол каждого слоя;
- прямой маршрут, SOCKS4a, SOCKS5 и HTTP CONNECT;
- UDP через SOCKS5 UDP ASSOCIATE;
- проверка сертификата, срока действия, SNI и ожидаемого текста страницы;
- уведомления Windows только при смене состояния;
- сводка и управление из системного трея;
- экспорт отчёта в CSV и JSON;
- установщик без прав администратора и portable EXE.

## Установка

Откройте **Releases** и скачайте:

- `popingui-<version>-x64.exe` — установщик NSIS с выбором каталога;
- `popingui-<version>-portable.exe` — переносимую версию без установки.

Сборки пока не подписаны коммерческим сертификатом, поэтому SmartScreen может показать
предупреждение. SHA-256 каждого файла публикуется в `SHA256SUMS.txt`.

## Как работает диагностика

| Слой | Методика | Что устанавливает |
|---|---|---|
| DNS | системный `getaddrinfo` сравнивается с DNS-over-HTTPS | нерабочий ответ при рабочем DoH указывает на вмешательство резолвера |
| PING | системный ICMP напрямую; ответ цели внутри TCP-туннеля через прокси | доступность и близкая к RTT задержка; отсутствие ICMP само по себе не считается блокировкой |
| TCP | соединение с указанным IP и портом | таймаут при доступном хосте указывает на фильтрацию IP/порта |
| TLS | handshake с настоящим SNI, разбор сертификата и срока | обрыв после TCP характерен для DPI по SNI; чужой сертификат — для перехвата |
| HTTP | `GET`, анализ статуса, redirect и тела | страницы-заглушки, чужие redirect и отсутствие ожидаемого текста |
| UDP | протокольная проба DNS/STUN/QUIC | доступность UDP; молчание QUIC подозрительно только при объявленном `alt-svc: h3` |

Расхождение DNS у CDN нормально, поэтому одного отличающегося IP недостаточно. При
провале системного маршрута выполняется контрольное соединение по адресу DoH. TLS и HTTP
запускаются только на соответствующих портах. Для UDP отправляются протокольные запросы,
а не случайный пакет. QUIC проверяется 1200-байтовым Version Negotiation probe.

Через прокси приложение не выдаёт время ответа локального proxy-процесса за ping цели:
туннель поднимается отдельно, затем измеряется payload, требующий ответа удалённого узла.
Подробное обоснование: [методики и справочник](docs/methodology.ru.md).

## Разработка

Требуются Windows и Node.js 22.12 или новее; CI использует Node.js 22.

```powershell
npm ci
npm run dev        # сервер :8787 + Vite :5273
npm run app        # Electron с hot reload
npm run typecheck
npm run check      # 12 локальных regression-проверок
npm run app:build  # NSIS + portable в release/
```

Проверки не зависят от внешнего интернета: они поднимают собственные DNS, HTTP, TLS,
QUIC и proxy-сервисы на loopback. Доказательства описаны в
[`.ai/verification.md`](.ai/verification.md).

## Архитектура

```text
Electron main ──┬── BrowserWindow ── React UI
                ├── Tray                 │
                └── Monitor ◄──── REST + WebSocket
                       ├── scheduler
                       ├── layered probe
                       ├── proxy / UDP transports
                       └── JSON persistence
```

`Monitor` — единственный владелец состояния. В packaged-приложении сервер работает
внутри Electron main process и слушает только `127.0.0.1`. Общие TypeScript-типы задают
контракт UI, сервера и трея. Подробнее: [архитектура](.ai/architecture.md).

## Ограничения

- результат описывает наблюдаемое поведение сети, а не юридическую причину ограничения;
- ICMP часто отключён владельцем узла и сам по себе не доказывает блокировку;
- PAC-скрипты системного прокси не исполняются;
- неподписанные сборки могут вызвать предупреждение SmartScreen.
