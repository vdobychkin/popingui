# Проверки

`npm run check` — все двенадцать подряд, около 75 секунд. Последовательно, а не
параллельно: половина скриптов занимает конкретные порты. Вывод показывается только у
провалившихся.

Тестового фреймворка нет намеренно. Каждый скрипт — самостоятельная программа, которая
поднимает на loopback ровно то, что нужно, и печатает человекочитаемый отчёт. Так проверка
заодно служит документацией: запустив её, видно не «12 passed», а что именно измерено.

## Что доказывает каждая

| Скрипт | Утверждение |
|--------|-------------|
| `check-interval` | шаги ползунка возрастают, границы 0,1 с и 10 мин, подписи и округление произвольных значений |
| `check-tray-menu` | проблемные цели на верхнем уровне, здоровые — нет; подменю содержит слои и рабочие пункты; пункт меняется на «Остановить» во время проверки; пустой список и подсказка |
| `check-system-proxy` | разбор `ALL_PROXY`/`HTTPS_PROXY`/`HTTP_PROXY`, устойчивый id, дедупликация одного адреса из двух источников, мусор не даёт записи |
| `check-transitions` | смены здоровья, питающие уведомления; первая проба не считается сменой |
| `check-proxy` | SOCKS5 с авторизацией и без, SOCKS4a по имени, HTTP CONNECT, и внятные ошибки на каждый отказ |
| `check-udp` | выбор пробы по порту, формат QUIC-пакета, распознавание ответов, релей SOCKS5 UDP ASSOCIATE (включая `BND.ADDR = 0.0.0.0`), отказ `0x07`, разбор `alt-svc`, три исхода `quicSilenceMeaning` |
| `check-probe-proxy` | сквозная проба через прокси: маршрут помечен, прокси реально использован, мёртвый прокси не даёт «доступен» |
| `check-tcp-ping` | пинг через прокси меряет путь до цели, а не до прокси; молчание не выдаётся за время; структура ClientHello |
| `check-latency` | какой слой даёт итоговую задержку на каждом маршруте, на двух видах SOCKS-серверов |
| `check-cert-and-expect` | просроченный, истекающий и чужой сертификат; ожидаемый текст. Требует `openssl`, без него пропускается |
| `check-threadpool` | пул libuv поднят выше умолчания и явное значение не перетирается |
| `check-scheduler` | пробы идут внахлёст, лимит соблюдён, медленная цель не тормозит быструю, одна цель не пробуется дважды, повторный запрос ждёт текущую пробу, пауза останавливает |

## Как добавить проверку

1. Файл `scripts/check-<что>.ts`, шапка-комментарий с описанием и командой запуска.
2. Счётчик `failures` и функция `check(name, ok, detail)` — как в остальных.
3. Поднимайте всё нужное на loopback. Живая сеть в проверках запрещена: она делает их
   медленными и лживыми. Единственное исключение — `check-system-proxy`, который
   *печатает* настройки этой машины, но ничего про них не утверждает.
4. `process.exit(failures ? 1 : 0)` в конце — `check-all.mjs` смотрит на код возврата.
5. Добавьте строку в `SCRIPTS` в `scripts/check-all.mjs` и в таблицы здесь и в
   корневом `README.md`.
6. **Проверьте, что проверка краснеет.** Временно сломайте то, что она утверждает,
   прогоните, убедитесь в падении, верните обратно. Две проверки в этом проекте были
   написаны так, что не могли провалиться.

## Занятые порты

Скрипты используют фиксированные номера, чтобы попадать в `TLS_PORTS`/`HTTP_PORTS` и в
таблицу UDP-проб: 8000, 8080, 8443, 8899, 3478, 784, 19302. Если порт занят, скрипт либо
берёт следующий кандидат (`bindAny` в `check-udp`), либо пропускает случай с пометкой
(`check-cert-and-expect`). Молча искажать результат нельзя.

## Проверка собранного приложения

```bash
npm run app:build
```

затем

```powershell
Start-Process -FilePath "release\win-unpacked\popingui.exe" -ArgumentList "--smoke" -Wait
Get-Content "$env:APPDATA\popingui\smoke.json" -Raw
```

Ожидается `"ok": true` и непустой `summary`. Если приложение уже запущено, отчёт будет
`{"ok": false, "ran": false}` — закройте экземпляр и повторите.
