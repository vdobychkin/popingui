# Устройство

## Три процесса, один поток данных

```
electron/main.ts ──┬── окно (BrowserWindow) ── src/ (React)
                   │                              │
                   └── трей (Tray + меню)         │ WebSocket + REST
                            │                     │
                            └──── server/app.ts (Monitor) ────┐
                                        │                     │
                                  server/probe.ts        server/store.ts
                                   (шесть слоёв)          (диск + память)
```

`Monitor` — единственный владелец состояния. Electron и React одинаково подписаны на
него: главный процесс через события `EventEmitter`, интерфейс через WebSocket. Никакого
второго источника правды нет, поэтому трей и окно не могут разойтись.

В упакованном приложении сервер живёт **внутри** главного процесса Electron: `main.ts`
импортирует `Monitor` напрямую, отдельного процесса нет. `server/index.ts` нужен только
для запуска без Electron (`npm run dev`, `npm start`).

| Файл | Ответственность |

| `server/proxy.ts` | `dial()`: TCP через SOCKS5 / SOCKS4a / HTTP CONNECT |
| `server/udp.ts` | UDP-пробы по протоколам и релей SOCKS5 UDP ASSOCIATE |
| `server/system-proxy.ts` | чтение прокси из реестра Windows и переменных окружения |
| `server/store.ts` | цели и настройки: память + JSON на диске, миграции старых файлов |
| `server/app.ts` | `Monitor`: HTTP+WS, планировщик, события |

## Ключевые типы

Всё в `shared/types.ts`, импортируется и сервером, и интерфейсом — тип, изменённый в
одном месте, ломает сборку в другом. Это намеренно.

- `LayerName` — `dns | ping | tcp | tls | http | udp`, порядок в `LAYER_ORDER`.
- `LayerSet` — какие слои включены; лежит **у каждой цели**, настройка задаёт только
  значение по умолчанию для новых.
- `Verdict` — не «доступен/недоступен», а *способ* недоступности: `dns-hijack`,
  `ip-block`, `tls-block`, `tls-mitm`, `http-stub`, `udp-silent` и так далее.
  `VERDICT_META` даёт подпись и тон (`good | warn | bad | idle`).
- `ProbeResult` — итог одной пробы: вердикт, задержка, `latencyFrom` (каким слоем
  измерена), маршрут, все слои с деталями.
- `ServerMessage` — размеченное объединение сообщений WebSocket: `snapshot`, `result`,
  `probing`, `sweep`, `settings`.

## Планировщик

У каждой цели своё расписание (`dueAt`), общая очередь и пул работников размером с
`concurrency`. Общего «прогона по списку» нет: медленная цель не задерживает быструю.

Инварианты, которые легко сломать:

- одна цель никогда не проверяется двумя пробами одновременно — иначе более старая
  запишет результат последней;
- очередь не растёт без предела: цель, уже стоящая в очереди, второй раз не ставится;
- пауза действительно останавливает, а не просто чистит очередь.

Всё три проверяются в `scripts/check-scheduler.ts`.

## Поток одной пробы

`probe(target, settings)` идёт слоями сверху вниз, каждый следующий опирается на
предыдущий:

1. **DNS** — системный резолвер против DoH. Даёт адрес для остальных слоёв.
2. **PING** — ICMP напрямую, TCP-пинг через прокси (ICMP не туннелируется).
3. **TCP** — connect на порт.
4. **TLS** — только на TLS-портах и только если TCP поднялся.
5. **HTTP** — только на HTTP-портах и только если TCP поднялся. Попутно достаёт
   `alt-svc`, без которого UDP-слой не может судить о QUIC.
6. **UDP** — тот же порт другим транспортом.

Через прокси имя резолвит прокси, поэтому `dialTarget` — это хост, а не адрес; провал
локального DNS при живом прокси ничего не останавливает.

Вердикт собирается одной лестницей `if/else if` в конце `probe()`. Порядок ветвей — это
приоритет: DNS-подмена важнее обрыва TLS, потому что чинить надо сначала DNS.
