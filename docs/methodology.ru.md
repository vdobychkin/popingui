# Методики и справочник popingui 1.0.0

Массовая проверка доступности ресурсов с диагностикой **способа блокировки**.
Приложение для Windows, живёт в трее.

Обычный пинг на заблокированном ресурсе бесполезен: хост чаще всего отвечает на ICMP,
а рвётся всё выше. popingui прогоняет каждую цель через шесть слоёв и по их комбинации
говорит не «недоступен», а *как именно* недоступен.

```bash
npm install
npm run app        # запуск из исходников
npm run app:build  # установщик и portable в release/
npm run check      # все проверки
```

## Слои и что они ловят

| Слой | Проверка | Что означает падение |
|------|----------|----------------------|
| DNS  | системный резолвер (`getaddrinfo`) против эталонного DoH | пустой ответ или служебный адрес при живом DoH — блокировка резолвером провайдера |
| PING | системный `ping` напрямую, TCP-пинг через прокси | почти ничего: ICMP режут у большинства CDN, поэтому это не вердикт |
| TCP  | connect на указанный порт | таймаут при живом ICMP — блэкхол по IP:порту |
| TLS  | handshake с **настоящим SNI** и проверкой сертификата | TCP поднялся, а handshake оборвали — DPI по SNI; чужой сертификат — перехват |
| HTTP | GET с браузерным User-Agent | распознаёт страницы-заглушки и редиректы на чужой хост |
| UDP  | тот же порт по UDP: QUIC на 443, запрос к резолверу на 53 | TCP проходит, а QUIC молчит — режут UDP, браузер молча откатывается на TCP |

### Контрольная проба

Расхождение адресов системного DNS и DoH само по себе ничего не значит — так работает
любой anycast/CDN. Поэтому при расхождении *и* провале соединения popingui повторяет
попытку по адресу от DoH. Открылось там и не открылось здесь — вот это уже подмена DNS.
Не открылось нигде — DNS ни при чём, виноват слой ниже.

## UDP и QUIC

Отдельный слой, потому что ловит то, чего не видит ни один из остальных: **TCP на 443
работает, а QUIC режут**. Браузер это скрывает — молча откатывается на HTTP/2 и работает
медленнее, а пользователь видит «просто тормозит» и не знает почему.

Главное свойство UDP: **молчание не значит ничего**. Рукопожатия нет, а ICMP Port
Unreachable до сокета не доходит (замерено: закрытый локальный порт не даёт никакой
ошибки). Отличить «порт закрыт», «пакет отфильтрован» и «сервис молчит на мусор»
невозможно. Поэтому единственный надёжный сигнал — ответ **по протоколу**, и проба
выбирается по номеру порта:

| Порт | Проба | Что считается ответом |
|------|-------|----------------------|
| 443, 8443, 784 | QUIC | любой пакет с длинным заголовком |
| 53, 5353 | DNS-запрос A-записи | ответ с тем же идентификатором и флагом QR |
| 123 | NTP, режим клиента | 48 байт в режиме сервера |
| 3478, 19302 | STUN Binding Request | magic cookie и тот же transaction id |
| остальные | нет пробы | слой пропускается: слать мусор и толковать тишину — гадание |

QUIC-проба намеренно дешёвая. Вместо Initial-пакета с шифрованием отправляется
long-header с заведомо неизвестной версией `0x0a0a0a0a`, на который сервер по RFC 9000
**обязан** ответить Version Negotiation. Ни ключей, ни AEAD, ни ClientHello — а ответ
тот же самый «да/нет». Пакет добит до 1200 байт: меньшие сервер вправе выбросить как
защиту от усиления.

### Почему молчание QUIC — ещё не блокировка

Бóльшая часть веба QUIC не раздаёт вовсе. `github.com` — как раз такой: TCP отвечает,
QUIC молчит, и ничего при этом не заблокировано. Красить такие цели в жёлтый значило бы
поднимать ложную тревогу на половине списка.

Поэтому решает объявление самого сервера: заголовок `alt-svc: h3=":443"` из HTTP-слоя.

- объявляет HTTP/3 и молчит по UDP → **находка**, вердикт `udp-silent`;
- не объявляет → так и должно быть, слой серый, вердикт не меняется;
- HTTP-слой выключен → сравнивать не с чем, слой жёлтый с пометкой «неизвестно», но
  вердикт не выносится.

Проверено на живой сети: `cloudflare.com` и `www.google.com` отдают `alt-svc: h3=":443"`
и отвечают на QUIC, `github.com` и `example.com` заголовка не отдают.

Оговорка: ответ на QUIC-пробу доказывает, что по этому адресу отвечает *что-то,
говорящее на QUIC*, а не что это сам источник. `example.com` отвечает Version
Negotiation, хотя HTTP/3 не объявляет.

### UDP через прокси

Работает только через **SOCKS5 UDP ASSOCIATE** (RFC 1928). HTTP CONNECT туннелирует
только TCP, у SOCKS4 команды для UDP нет вовсе, Tor тоже TCP-only. Это не сбой цели, а
свойство маршрута, поэтому слой пропускается с явной причиной, а не падает.

Три вещи, которые пришлось учесть:

- TCP-соединение с ASSOCIATE держится открытым всё время жизни ассоциации — закрыл,
  релей умер;
- `BND.ADDR = 0.0.0.0` в ответе означает «тот же хост, что и управляющее соединение», и
  слать на `0.0.0.0` бессмысленно;
- время самого ASSOCIATE идёт по TCP и о UDP-пути не говорит ничего — из замера
  исключается, ровно как время туннеля в TCP-пинге.

Замеры через локальный xray (SOCKS-вход, UDP включён): QUIC до `google.com` — 90 мс
напрямую и 404 мс через прокси, DNS до `1.1.1.1` — 109 и 298 мс.

Всё проверяется в `scripts/check-udp.ts` на loopback: свой резолвер, свой QUIC-сервер,
свой SOCKS5 с релеем, прокси с отказом `0x07` и релей, отвечающий `0.0.0.0`.

## Приложение для Windows

Собрать установщик NSIS и portable-exe в `release/`:

```bash
npm run app:build
```

Получится `release/popingui-1.0.0-x64.exe` (установщик, можно выбрать папку, без прав
администратора) и `release/popingui-1.0.0-portable.exe` (запускается как есть).

Запустить приложение из исходников (Vite с hot reload + Electron):

```bash
npm run app
```

Приложение живёт в системном трее. **Правый клик по иконке** разворачивает отчёт:

- сводка «столько норма · столько странно · столько блок» и время последней проверки;
- каждый проблемный ресурс отдельным пунктом, в подменю — вердикт словами, все слои
  с их статусом и задержкой, адрес, аптайм, кнопки «Показать в окне» и «Перепроверить»;
- подменю «Все ресурсы» с тем же разбором по каждой цели;
- «Проверить всё» / «Остановить проверку», «Скопировать отчёт (CSV)» в буфер обмена,
  переключатель «Запускать при входе в систему», «Выход».

Иконка трея меняет и цвет, и форму по худшему статусу: сплошной круг — норма,
кольцо — есть странности, круг с прорезью — есть блокировки. Форма, а не только цвет,
чтобы состояние читалось при дальтонизме и на пёстром фоне панели задач.

Левый клик по иконке показывает и прячет окно. Закрытие окна не выключает мониторинг —
приложение сворачивается в трей; выход только через пункт меню. Второй запуск не поднимает
вторую копию, а показывает уже работающую.

Настройки и список целей лежат в `%APPDATA%\popingui\data`.

## Формат списка целей

Одна строка — один ресурс, всё после первого пробела/запятой — заметка:

```
example.com
https://rutracker.org
1.1.1.1:53 DNS Cloudflare
my-host.local:8080 # внутренний сервис
```

Поддерживаются URL со схемой и путём, `host:port`, голые IP. Порт по умолчанию — 443.
Есть импорт из текстового файла и выгрузка результатов в CSV/JSON (`/api/export?format=csv`).

## Частота опроса

Ползунок стоит в шапке окна — частоту меняют чаще всего остального и обычно прямо во
время наблюдения за результатами. Диапазон — от `0,1 с` до `10 мин`, и идёт он не линейно,
а по набору шагов:

```
вручную · 0,1 с · 0,2 с · 0,5 с · 1 с · 2 с · 3 с · 5 с · 10 с · 15 с · 20 с
        · 30 с · 45 с · 1 мин · 1 мин 30 с · 2 мин · 3 мин · 5 мин · 7 мин 30 с · 10 мин
```

Тринадцать делений умещаются в первую минуту: именно там разница осмысленна, а линейная
шкала сплющила бы её в пару пикселей. Крайнее левое положение выключает автопрогон.

Значения меньше `0,1 с` сервер поднимает до `0,1 с`, даже если пришли прямо в API, —
иначе планировщик превращается в холостой цикл. Настройки, сохранённые прежними версиями
с интервалами в часы, ложатся на ближайший шаг (`10 мин`).

## Пинг через прокси

ICMP по SOCKS и HTTP CONNECT не проходит: оба туннелируют только TCP, а ping это не TCP.
UDP ASSOCIATE тоже не выход — ICMP не UDP, и прокси его не ретранслируют.

Поэтому слой называется **PING**, а не ICMP: он отвечает на вопрос «жив и как быстро», а
метод зависит от маршрута. Напрямую уходит настоящее ICMP-эхо.

Через прокси мерить время установки соединения нельзя — и именно отсюда брались
неправдоподобные «2–3 мс». Локальный SOCKS- или HTTP-клиент (shadowsocks, xray, Tor,
большинство VPN-помощников) отвечает на CONNECT сразу, как только разобрал запрос, а
наружу идёт потом. Измерялся, таким образом, круг до процесса на этой же машине.

Сейчас время открытия туннеля из результата исключено: туннель поднимается отдельно,
затем в него уходит то, на что цель обязана ответить (ClientHello на TLS-портах,
`HEAD /` на HTTP-портах), и замеряется ожидание ответа — настоящий круг до цели.
Ответом считается и FIN, и RST: цель отказалась говорить, но отказ прошёл весь путь.

Замеров три, берётся **лучший**: минимум ближе всего к настоящему времени пути, потому
что накладные расходы могут только добавляться. Время до самого прокси не выбрасывается,
а показывается в деталях отдельной строкой — вместе с пометкой «ответ на CONNECT
досрочный», если прокси ответил раньше, чем подключился.

Если туннель открылся, а цель промолчала, слой даёт предупреждение без числа: соединение
есть, времени пути нет, и выдавать за него время до прокси нельзя.
Проверено в `scripts/check-tcp-ping.ts`.

## Что проверять у каждого ресурса

Набор слоёв выбирается **для каждой цели отдельно** — при добавлении галочками рядом
с полем ввода, а позже в панели ресурса, в разделе «Слои» прямо над списком результатов.
Настройка в общих настройках задаёт только значение по умолчанию для новых целей и не
меняет задним числом то, что уже добавлено.

Полезно, когда в списке разнородные ресурсы: игровому серверу не нужен HTTP, внутреннему
хосту в локальной сети не нужна сверка DNS с DoH, а голому IP — сам DNS.

Изменение сохраняется сразу, а перепроверка запускается с задержкой в полсекунды: снять
три галки — это одно решение, а не три повода гонять пробу. Последний включённый слой
снять нельзя — цель без единой проверки висела бы в списке, ничего не сообщая.
Выключенные слои показываются в результатах как `выключен`, а не исчезают: иначе было бы
не отличить «не проверяли» от «проверили и нечего сказать».

## Как устроен опрос

У каждой цели своё расписание, общего «прогона по списку» нет. Цель становится готовой
к проверке через выбранный интервал после того, как завершилась её собственная прошлая
проверка, и попадает в общую очередь; из очереди её забирает свободный работник, а
работников ровно столько, сколько указано в параллельности.

Отсюда три следствия:

- **Проверки идут внахлёст.** Быстрая цель не ждёт, пока медленная досчитает свой таймаут.
- **Ничего не пропускается.** Прежняя схема отказывалась начинать новый прогон, пока шёл
  предыдущий, поэтому при коротком интервале циклы молча терялись.
- **Ничего не накапливается.** Одна и та же цель никогда не проверяется дважды
  одновременно, а очередь ограничена числом целей — при 0,1 с не возникает лавины
  наложенных прогонов.

Последнее относится и к ручной перепроверке, а не только к расписанию: запрос по цели,
которая прямо сейчас проверяется, ждёт окончания текущей пробы. Иначе две пробы наперегонки
пишут один и тот же результат, и более старая — запущенная со старыми настройками — может
записаться последней. Виднее всего это при редактировании слоёв: в таблице оставался ответ
от слоя, который только что выключили.

Замерено в `scripts/check-scheduler.ts`: на двух локальных целях (мгновенная и с задержкой
1,5 с) при интервале 0,1 с быстрая успевает 60 проверок за 9 секунд, медленная — 5, пик
очереди 0, лимит параллельности соблюдён. Одновременность считают сами цели-серверы, а не
счётчик `inFlight` монитора: тот хранит идентификаторы в `Set` и по построению не может
показать одну цель дважды, поэтому проверка через него ничего не доказывала.

Индикатор в шапке показывает, что происходит прямо сейчас: крутящийся кружок и число
активных проб (плюс размер очереди, если она есть), `ожидание` в паузах между кругами
и жёлтое `пауза`, если опрос остановлен кнопкой.

У каждой строки свой индикатор в колонке статуса: кружок со счётчиком секунд, пока цель
проверяется, и `в очереди` с приглушённым фоном, пока она ждёт свободного работника.
Счётчик — самое полезное здесь: он сразу показывает, **кто именно держит очередь**, а
после трёх секунд становится жёлтым.

Столбцы «Ресурс», «Статус», «Задержка» и «Аптайм» кликабельны: первый клик сортирует,
повторный переворачивает порядок, стрелка показывает текущий. Строки без замера всегда
остаются внизу — иначе разворот сортировки по задержке поднимал бы наверх то, что вообще
не измерено.

Подпись рядом с ползунком показывает длительность полного круга по всем целям. Если круг
длиннее интервала, она желтеет: цели, чья проверка сама по себе дольше интервала, просто
не могут опрашиваться так часто — остальные при этом сохраняют свой темп.

### Почему таблица не дёргается

Ширины столбцов заданы явно (`table-fixed` плюс `colgroup`), растягивается только колонка
ресурса. Иначе ширины считались бы по содержимому, и каждая проверка сдвигала бы всю
строку — статус то `Сертификат просрочен`, то счётчик секунд, то короткое слово.

По той же причине подписи в шапке заменены значками: старт и стоп — одна квадратная
кнопка 28×28, которая при смене состояния не меняет размер, счётчики светофора и статус
в таблице — фиксированные глифы. Название каждого значка есть в `title` и в подписи для
экранного диктора; форма у значков разная, а не только цвет, — как и у иконки трея, чтобы
состояние читалось при дальтонизме.

## Что означает «Задержка»

Рядом с числом указан слой, которым оно измерено, — это не одно и то же расстояние
в разных строках:

- **PING** — один круг до цели и обратно. Ближе всего к настоящему RTT, поэтому берётся
  первым, если этот слой дал результат.
- **TCP** — установка соединения. На прямом маршруте это тоже один честный круг.
- **TLS** — рукопожатие: несколько кругов плюс работа сервера.
- **HTTP** — весь запрос вместе с ответом, заметно больше чистого RTT.

Через прокси TCP-слой намеренно уходит в самый конец очереди. Причина: прокси отвечает на
CONNECT либо после того, как сам подключился к цели (тогда время честное), либо сразу,
а к цели идёт потом — и тогда цифра равна задержке только до прокси. Со стороны клиента
эти два случая неразличимы, поэтому на прокси-маршрутах цифра из TCP не используется,
пока есть хоть один слой, прошедший весь путь. Проверено в `scripts/check-latency.ts` на
двух SOCKS-серверах, ведущих себя обоими способами, и в `scripts/check-tcp-ping.ts`, где
прокси отвечает досрочно, а канал добавляет заметную задержку.

Про ICMP: время берётся из вывода системного `ping`, а он локализован и печатается в
кодировке консоли (для русской Windows — 866). Буфер декодируется несколькими кодировками,
пока не найдётся число. Если не нашлось, слой сообщает, что цель отвечает, но **без
числа**: подставить туда время работы `ping.exe` значило бы показать десятки миллисекунд,
которых не было в сети.

## Уведомления

Приложение сообщает о смене статуса всплывающим уведомлением Windows. Переходы
собираются в пачку за три секунды и отправляются **одним** уведомлением, а не по одному
на цель: на фильтрующей сети десяток ресурсов падает одновременно, и очередь тостов была
бы нечитаемой. Первая проверка каждой цели молчит — иначе список заблокированного
объявлялся бы как «только что сломалось».

В настройках: только о проблемах (по умолчанию), о проблемах и восстановлении, выключены.
Клик по уведомлению открывает окно, а если ресурс был один — сразу его карточку.

Уведомления Windows привязаны к ярлыку в меню Пуск, поэтому надёжнее всего они работают
у версии, установленной через `popingui-1.0.0-x64.exe`.

## Срок действия сертификата

TLS-слой и так забирает сертификат, поэтому заодно проверяется срок: просроченный даёт
вердикт «Сертификат просрочен» (браузер такой сайт уже не откроет), меньше 14 дней до
конца — «Сертификат истекает» жёлтым, не мешая остальным вердиктам. Точная дата и число
дней видны в панели деталей.

Проверка сертификата важна именно потому, что popingui подключается с отключённой
проверкой цепочки — иначе не удалось бы рассмотреть враждебный сертификат при подмене.
Значит, даты никто, кроме этого кода, не проверяет.

## Ожидаемый текст в ответе

У каждой цели в панели деталей есть поле «Ожидаемый текст в ответе». Если задан и в ответе
его нет — вердикт «Нет ожидаемого текста». Встроенный список маркеров заглушек знает только
те страницы блокировки, что уже попадались; это поле закрывает остальные. Поле сохраняется
само, через полсекунды после того, как вы перестали печатать.

## Проверки через прокси

В шапке — переключатель маршрута. «Напрямую» показывает, что видит эта сеть сама;
выбор прокси гоняет те же проверки через него.

Если прокси настроен в самой системе, он появляется в списке отдельной группой
«Настроен в системе» — вводить его руками не нужно. Читается то, чему подчиняется
остальной софт: переменные `ALL_PROXY` / `HTTPS_PROXY` / `HTTP_PROXY` и, на Windows,
ключ `Internet Settings` в реестре, откуда берут настройки Chrome, Edge и всё на WinINET.
Выключенный в системе прокси (`ProxyEnable = 0`) не предлагается. Список перечитывается
при открытии переключателя, поэтому прокси, включённый в Windows при работающем
приложении, появится без перезапуска.

Системные записи не сохраняются в файл настроек и не удаляются из панели: они зеркалят
систему, и копия на диске пережила бы настройку, которую отражает. Выбранный маршрут при
этом запоминается — если запись найдётся при следующем запуске, она снова станет активной.

PAC-скрипты (`AutoConfigURL`) намеренно не поддерживаются: чтобы узнать прокси, пришлось
бы выполнять чужой JavaScript для каждой цели, и ответ был бы разным для разных целей —
это уже не маршрут, который можно выбрать в переключателе. Смена маршрута сразу перезапускает
прогон, поэтому в таблице никогда не смешиваются замеры, снятые разными путями:
строки, полученные через прокси, помечены бейджем, а точный маршрут виден в панели
деталей, в CSV-выгрузке и в меню трея.

Поддерживаются SOCKS5 (в том числе с логином и паролем), SOCKS4a и HTTP CONNECT.
Формат строки — `схема://[логин:пароль@]хост:порт  Название`; без схемы считается
SOCKS5, текст после адреса становится названием:

```
socks5://127.0.0.1:1080  Локальный SOCKS
http://user:pass@proxy.example:3128  Рабочий HTTP
127.0.0.1:9050  Tor
```

Кнопка «Проверить» рядом с прокси пробует поднять через него соединение и отвечает
«работает, N мс» или конкретной ошибкой — чтобы не искать блокировку там, где просто
лёг сам прокси.

Что меняется при работе через прокси:

- **DNS** — имя резолвит прокси, а не система. Ресурс, который открывается только так,
  почти наверняка заблокирован на уровне DNS провайдера.
- **PING** — переключается на TCP-пинг: ни SOCKS, ни CONNECT не туннелируют ICMP.
  Время открытия туннеля в результат не входит, см. «Пинг через прокси».
- **Определение DNS-подмены** — отключается: ответ системного резолвера в этом режиме
  всё равно не используется, сравнивать нечего.

## Настройки

Параллельность (сколько проверок идёт одновременно), таймаут слоя, адрес эталонного
DoH-резолвера, режим уведомлений и включение/отключение отдельных слоёв. Частота опроса
вынесена ползунком в шапку главного окна.

## Структура

| Путь | Что там |
|------|---------|
| `server/probe.ts` | шесть слоёв проверки и свод вердикта |
| `server/proxy.ts` | дозвон через SOCKS5 / SOCKS4a / HTTP CONNECT |
| `server/udp.ts` | UDP-пробы (QUIC, DNS, NTP, STUN) и релей SOCKS5 UDP ASSOCIATE |
| `server/system-proxy.ts` | чтение прокси из реестра Windows и переменных окружения |
| `server/store.ts` | хранение целей и настроек, миграции старых файлов |
| `server/app.ts` | класс `Monitor`: HTTP+WS, планировщик, события для трея |
| `server/index.ts` | запуск сервера отдельным процессом |
| `electron/main.ts` | окно, трей, автостарт, единственный экземпляр |
| `electron/tray-menu.ts` | построение меню трея — чистая функция |
| `src/` | интерфейс на React |
| `scripts/make-icons.mjs` | генерация PNG и .ico кодом, без бинарников в репозитории |
| `scripts/check-all.mjs` | прогон всех проверок одной командой (`npm run check`) |
| `scripts/check-tray-menu.ts` | меню трея на синтетических данных |
| `scripts/check-proxy.ts` | протоколы прокси против локально поднятых серверов |
| `scripts/check-probe-proxy.ts` | сквозная проба через прокси, всё на loopback |
| `scripts/check-cert-and-expect.ts` | сроки сертификатов и ожидаемый текст, сертификаты генерирует openssl |
| `scripts/check-transitions.ts` | смена статуса, питающая уведомления |
| `scripts/check-latency.ts` | что именно меряет задержка на каждом маршруте |
| `scripts/check-interval.ts` | шаги ползунка частоты и их подписи |
| `scripts/check-scheduler.ts` | параллельность проверок, лимиты и пауза |
| `scripts/check-threadpool.ts` | во что упирается пул потоков libuv |
| `scripts/check-udp.ts` | UDP-пробы, релей SOCKS5 и разбор `alt-svc` |
| `scripts/check-system-proxy.ts` | чтение прокси из системы и переменных окружения |
| `scripts/check-tcp-ping.ts` | что меряет пинг через прокси, отвечающий на CONNECT досрочно |

Все проверки разом — `npm run check` (около 75 секунд, вывод падавших скриптов
печатается целиком). Проверка типов — `npm run typecheck`.

Самопроверка собранного приложения без ручного клика: `popingui.exe --smoke` поднимает
всё, пишет `%APPDATA%\popingui\smoke.json` с состоянием трея, окна и сервера, и выходит.

## Ограничения

- ICMP выполняется через системный `ping`, потому что raw-сокеты на Windows требуют прав
  администратора. Вывод парсится с учётом локализации (`time=12ms` / `время=12мс`).
- TLS-слой запускается только на портах, где TLS ожидается (443, 8443, 993, 995, …),
  HTTP-слой — только на HTTP-портах. На остальных портах вердикт строится по TCP.
- Проверка показывает картину **с той машины, где запущена**. Это её задача, но помните:
  в сетях с прозрачным TCP-прокси (часть корпоративных сетей, песочницы) connect успешен
  к любому адресу, и слой TCP перестаёт быть показательным.
- Список маркеров страниц-заглушек в `server/probe.ts` (`STUB_MARKERS`) — дополняйте под
  своего провайдера.
- UDP-слой у **уже добавленных** целей выключен: включать проверку задним числом значило
  бы менять их поведение без спроса. У новых целей он берётся из настроек по умолчанию —
  но настройки, сохранённые до появления слоя, тоже приходят с выключенным UDP, так что
  первый раз его нужно включить руками: «Настройки → Слои для новых ресурсов», либо у
  конкретной цели в её панели.
- Молчание по UDP на порту, где сервер не объявляет HTTP/3, вердикта не меняет — иначе
  половина списка светилась бы жёлтым без всякой блокировки.
